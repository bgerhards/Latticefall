For fifty-one pull requests, merging closed nothing at all

PRC

The owner noticed something small: the loop ships a pull request, the pull request merges, and the issue is still sitting in the backlog. It turned out to have never worked once. PR #130 had merged thirty-seven minutes earlier carrying the line “Closes PLC-03”, and issue #31 was still open with closedAt null — because GitHub acts only on Closes #31, and a spec id in backticks is prose it reads straight past. Across all fifty-one merged pull requests in the repository, zero carried a closing keyword GitHub could resolve. The fix is not a script that closes things; it is making the merge itself the close, which is the only version that works when the owner merges by hand — and hand-merging is precisely the case every previous mechanism missed.

The report was one sentence: *the Python script runs, the task completes, it creates the pull request, I merge it — and the issue still sits in the backlog. Is that behaviour we anticipate?*

It is not. And the thing that made it worth stopping for was how recently it had failed. Pull request #130 had merged thirty-seven minutes earlier, closing the firing-arc work, with this line at the top of its body:

Closes PLC-03. Decision 078.

GitHub issue #31 was still OPEN, closedAt: null. GitHub acts only on Closes #<number>. A spec id in backticks is prose, and it reads straight past it. The line looked exactly like a closing keyword, was written in good faith, and did nothing whatsoever.

That last number needs a caveat, and the caveat is the actual finding. Forty is not forty stale items. A pull request naming LF-211 may have *filed* it rather than fixed it — which is exactly what #130 did. Nothing in the repository distinguishes “this PR fixed it” from “this PR mentioned it,” and *that indistinguishability is the defect*, not a footnote on it.

Three holes, none of them the one that was obvious

  • No workflow observes a merge. gate.yml, parity-shard.yml and parity-windows.yml all trigger on open and synchronize only. Nothing runs on pull_request: closed.
  • tools/issues.py close is a line in a prompt. It is a good tool, and it lives in the autoloop's brief and in step 8 of the ship skill — which means when the owner merges by hand, no code runs at all. Decision 051 exists because remembered rules fail. This was a remembered rule wearing a tool's clothes.
  • Two tracking systems that had never been introduced. backlog.json holds LF-nnn and closes with backlog.py done; docs/issues/*.md projects to GitHub and closes with issues.py close. The ship loop touched the second and never the first.

The fix is not a closing script

The temptation was a workflow on pull_request: closed that goes and closes things. That is another mechanism to forget, and it does nothing about the backlog file. The better answer was to ask what each system actually *is*.

A docs/issues/ spec is projected to something outside the repository, so the close has to happen outside too — and GitHub already does it, atomically, on merge, no matter who presses the button. So the pull request body carries a *resolved* Closes #31, looked up from the id map rather than typed by hand.

A backlog.json item is a file inside the repository. Nothing external needs telling. It is marked done in the pull request's own commit, so merging is what lands the close and there is no second step at all.

Both halves read one declaration — a Closes: trailer in a commit message. The colon is load-bearing. It is git's own trailer syntax, so a sentence like “this closes the gap LF-105 describes” cannot be mistaken for a declaration. Both shapes were tested.

Proven red, then green, then red again

A check nobody has watched fail is a check nobody should trust. The new tier-1 issue traceability check was driven through both states on the real branch: green with LF-212 marked done, then red after reopening it — naming the commit, the id and the exact command to fix it — then green again. The CI-side half was driven with the literal body of PR #130, which it correctly refuses, and with a body containing shell-injection-shaped text, which passes through the environment untouched because the workflow never puts a pull request body on a command line.

What this cost, said plainly

Tier 1 went from about 7.8 s to 8.3 s against a 10 s budget. Tier 2 is at 33,386 ms against a 28,000 ms budget — over, and it was already over before this landed (LF-178). This added roughly 370 ms to that. The budget did not move, because moving it is the thing decision 067 refused to do when it deleted PRESSURE_FLOOR rather than raising it. The honest state is: tier 2 needs a check taken out, not a bigger number.

Two traps found on the way

actions/checkout defaults to depth 1, so git merge-base origin/main HEAD finds nothing — and the new check would have reported *“skip: no merge base”*: green, and useless. That is the exact partial-run-that-reads-as-full this gate is built to refuse, so both jobs now fetch full history. The pack is about 7 MiB with LFS excluded.

And the tier counts check caught the docstring drift this change introduced on the very first run, which is precisely what it is for.
