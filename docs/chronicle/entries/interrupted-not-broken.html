Interrupted, not broken

PRC

The earlier entry today, “The autoloop had no instrument panel and no brake,” closed on an open question: the spawned session's first run had died instantly with a 15-byte log reading “Execution error,” filed as LF-209. This corrects a claim made a few hours earlier in the same session, in “The autoloop had no instrument panel and no brake.” That entry ended on an open question, filed as LF-209: the autoloop's first spawned session had died instantly, its whole log 15 bytes reading “Execution error,” and the conclusion drawn from that was that the loop's plumbing was now fixed but the thing it launched still did not work. That conclusion was wrong, and the reason it was wrong is worth recording as carefully as the original claim was.

The evidence had been on disk the whole time

The session transcript under ~/.claude/projects/ for that run was never read before LF-209 was filed. Read afterward, it shows about three minutes of real work: /session-start completed, the PLC-07 spec was read, and a godot-engineer subagent was being dispatched when the transcript ends on [Request interrupted by user for tool use]. The session was not broken. It was interrupted — by the owner's own Ctrl-C. claude -p prints exactly “Execution error” when a run is aborted, and the log is 15 bytes for the plainest reason available: a session that never finishes emits no final text.

The real defect was worse, and it shipped in the fix hours earlier

Ctrl-C is delivered to the terminal's foreground process group, not to a pid. The child session lived inside the loop's own process group, so the terminal's signal reached it directly, and the parent's brand-new SIGINT handler — the one the earlier entry described as turning one Ctrl-C into a graceful stop — never got a turn to decide anything. “One Ctrl-C finishes the current issue” could not have held for a single run; it only ever looked like it might because nobody had pressed Ctrl-C against the fixed version yet. start_new_session=True now detaches the child into its own group, so a terminal Ctrl-C reaches only the loop.

Reproduced both ways, not reasoned about

A harness that signals the process group exactly as a real terminal does was run against both versions. Without the fix, the child prints:

CHILD KILLED BY THE TERMINAL Ctrl-C

and with it:

CHILD FINISHED ITS WORK

Detaching moves the risk rather than removing it

A detached child is a process-group leader, so a deliberate kill now goes through killpg rather than a plain kill() on its pid — killing the pid alone would strand its own subagents, its Godot, its Blender as reparented survivors, which on this project is a money bug and not fan noise. And because a detached child no longer dies for free when the loop does, its pid is now printed to the console and written to .cache/autoloop-status.json: a kill -9 on the loop leaves a live agent session running with nobody watching it, and whoever has to end it by hand needs the number rather than a process listing to hunt through. That gap — the reaper does not yet know how to find or check that pid on its own — is open as LF-210.

LF-209 is dropped, not closed

The bug it described does not exist. The cheaper lesson is the one worth keeping: the transcript under ~/.claude/projects/ answers “what did the spawned session actually do” in seconds, and guessing from a 15-byte log instead produced a wrong diagnosis that survived a merge and into a published journal entry.
