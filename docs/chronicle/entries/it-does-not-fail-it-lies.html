Five slices hand-rolled the same count, and the trap all five rediscovered does not fail — it lies

BALPRCdecision 094

Decision 094. BAL-04's acceptance criteria had been recomputed from the grader's JSON in a scratch script five times across two days, and each time the same three traps had to be found again — chief among them that a built entry carries its coordinates, so a membership test against bare tower ids matches nothing and answers a confident zero without raising. They now have tools/criteria.py, a stored baseline artefact that carries the commit it was taken on, and a tier-1 gate check that drives all six comparators red as well as green. No data file changed.

The previous entry, a-threshold-with-a-history, ended by reporting one of its own items as not closed: two build-parsing helpers now existed in tools/density.py and nothing anywhere called them. This entry is that item, an hour later, and it is the fifth and last of the day. tools/criteria.py and tools/bal04_baseline.json are new; tools/check.py, tools/density.py and the docs are the rest of it. No data file changed, so nothing about the game moved — what moved is what the project can now assert about it.

The problem is a count

Decisions 088 and 089 on the 4th, then 090, 091 and 093 today, each recomputed BAL-04's multi-weapon coverage and its per-anchor standard + brutal distinct-winning-build figures out of sim/run.py's JSON in a scratch script. Five slices, five scripts, and each one had to rediscover the same three traps.

  • A built entry is "<tower-id>@<x>,<y>". A membership test against bare tower ids matches nothing and reports a confident zero. That is the whole danger and it is worth stating flatly: it does not fail, it lies. Nothing raises, nothing comes back empty, and the number that arrives looks exactly like a finding.
  • sim/run.py --json silently drops each report's runs unless --detail is also passed (LF-258). A per-run statistic computed off such an artefact gets nothing and says nothing.
  • "Achievable" means at least two weapon ids unlocked — damage > 0 — at or before the anchor. That is the difference between 17 of 22 and 17 of 24 as decision 088 recorded it, and getting it wrong makes anchor-01 and anchor-02 permanent failures, since each unlocks exactly one weapon. It is the exact error decision 088 had to correct.

And decision 093 — an hour before this one — added the @-splitting helpers to tools/density.py but nothing called them, which is LF-278. An uncalled helper is not a fixture; it is a claim nobody checks.

Why a tool, and not more fields on the grader

The obvious cheaper move is to have sim/run.py --json emit these figures directly. It was rejected, and the argument is good enough to keep. The grader's report is per anchor, and four of the six criteria are not. Three compare the whole campaign against a stored baseline; the count: 1 share is computed from data/anchors/ and never touches a grade at all. Putting them behind --json would make every consumer of that instrument carry BAL-04's specification plus a baseline file it never asked for, and would give sim determinism — which diffs two grade runs byte for byte — a second thing to be sensitive to. The grader answers "is this anchor sound"; this answers "did the campaign get worse than the day we wrote the bar down", and those are different questions with different inputs.

Consuming the grade instead of extending it also escapes LF-258 structurally rather than by remembering a flag. With no --grade the tool grades in-process, so runs is always present and the --detail trap cannot be reached. Handed a saved artefact that has no runs, the multi-weapon criterion fails loudly instead of reporting 0 of 22.

The bar is an artefact, and it carries the commit it was taken on

tools/bal04_baseline.json is a tracked file next to tools/parity_costs.json, which is the same idea for a different measurement. Nothing in the tool hardcodes a per-anchor number, because decision 088's finding is precisely that the bar is per anchor and measured rather than a flat constant. It records the commit it was taken on — the discipline LF-271 asked for after LF-218's quoted figures stopped reproducing — and --rebaseline is the only way it moves. That flag writes improvements without ceremony, refuses to write a regression unless --accept-regressions is passed and names each one it would bake in, and refuses outright on a partial grade, so a one-anchor run can never become the campaign's bar.

The detail most worth keeping: integers, compared by cross-multiplication

The count: 1 shares are stored as {count_one, entries} integers and compared by cross-multiplication, never as a stored percentage. Act I's bar is 15 of 191 spawn entries. A stored 0.079 would have admitted 16 of 203 = 7.882% as "no rise" — a regression passing as a rounding artefact. Same class of error as decision 087's population confound: the number was right and the comparison was not.

Criterion 4 delegates, and three checks are deliberately absent

The PLC-05 saturation denominator already has three copies in this repository — validate_data.py, tools/sweep.py, and density._tower_max_draw — each carrying a comment telling the next person to move the other two. A fourth would be a fourth thing to drift, and the criterion as BAL-04 writes it is that tool's verdict, so criterion 4 runs it and reports what it said. The measured headroom is printed beside it as context and is not asserted.

For the same reason, three of BAL-04's remaining acceptance bullets are absent rather than implemented: wave density, dialog capacity and rules parity are gate checks that already fail loudly on their own, and a second, weaker copy of a check that exists is worse than no copy. The restraint is the point — a tool that covers everything covers some of it badly.

One helper became two, and the reason is in the docstring

Giving the helpers a caller turned up something the helpers themselves could not have known. BAL-04's multi-weapon criterion conditions on an anchor's unlocked roster, which is a list of bare tower ids and not a build. Passing it through build_tower_ids() would have worked — a bare id survives the @ split unchanged — and would have been the wrong thing to read in six months. So the weapon predicate was split out as weapon_ids(), and weapon_ids_in_build() became one line on top of it: one predicate, two entry points, no third copy. Code that is correct by accident is a defect with a delay on it.

Proved against a known answer, then proved red

It reproduces the record exactly on a4702df: 24/24 ok, multi-weapon 22/22 achievable, campaign win share 44.8 / 31.2 / 25.1 falling strictly, act 1 count: 1 at 7.9%. Two further known-answer checks were run rather than assumed. The per-anchor table is greater than or equal to decision 088's eight figures on all eight, consistent with decision 090's "nine anchors improved"; and multi-weapon is 22/22 under both readings of the criterion's wording — "any winning run" and "standard only" — so the looser phrasing is not currently hiding anything.

Then all six criteria were driven to failure: a not-ok anchor, a partial grade, a grade missing brutal, one anchor losing a build, an anchor's winners going single-weapon, an artefact with no runs, capacity at 85% and at 110% of saturation, one spawn entry moved to count: 1, brutal made forgiving, and a top tier equal to its base. The gate check was proved red three ways as well — a comparator hardwired to ok, a stale docstring count, and by removing the @ split, which is the trap the whole tool exists for.

Restores were asserted, not assumed. A git ls-files plus sha256sum manifest over all 1,519 tracked files diffs clean before and after. Perturbations ran against copies in the scratchpad, and the two that had to read data/ ran inside an isolated git worktree, so the shared working tree was never written — which matters on a machine where the owner plays out of the same directory an agent edits.

A stale bar, found by building the tool

docs/issues/BAL-04-regrade-the-campaign.md is where these criteria were written down, and its acceptance section was still quoting multi-weapon 17/22 and act 1 at 10.1% — both superseded, by decisions 090 and 091 respectively. Its per-anchor list was decision 088's, measured at 54c666b, and five of those eight anchors have since improved.

The issue now points at the artefact and keeps the superseded numbers marked rather than deleted, per the same append-only rule this journal runs on. CLAUDE.md's Commands block gains the tool.

Filed, not fixed

LF-279. sim/run.py --json should error when a consumer needs runs and --detail was absent, rather than emitting reports that quietly have none. tools/criteria.py routes around it by grading in-process, which means the trap is closed for this tool and still live for the next hand-rolled script. Routing around a trap is not the same as removing it, and the difference is worth a ticket.

The lesson, which is the mechanical half of decision 088

Decision 088 said that an acceptance criterion carries the baseline it is judged against, or it is not a criterion. This is the other half of that sentence: a baseline that lives in prose is a baseline that goes stale between the session that writes it and the session that reads it. Five hand-rolled scripts, three rediscovered traps and one issue quoting three superseded figures is what that costs — and none of it was ever visible as a failure, because a hand-rolled count that is wrong looks exactly like a hand-rolled count that is right.
