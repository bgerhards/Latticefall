Quality is not just looks: four owner-gated decisions taken at last

ARTBALPRCTERWARdecision 066decision 067decision 068decision 069

The owner delegated four questions that had sat gated for sessions, in one message, with one instruction: "quality > speed > cost, and quality is not just looks — if we are sacrificing performance, that's a no no." All four were taken rather than deferred back — the atlas stays at 256 px on a VRAM number, a check measured dead twice is deleted rather than raised, tabs win over a 6,000-line branch that existed only to argue back, and line of sight and the regional power grid close outright rather than sit as merely unscheduled. The same commit also names what the delay itself cost: a 29-minute wrap the owner never asked to sit through.

Four questions had been sitting owner-gated for sessions. The owner delegated all four at once, in their own words: "quality > speed > cost, and quality is not just looks — if we are sacrificing performance, that's a no no." What came back was not four answers written up for later review. It was four decisions, 066 through 069, taken in a single commit — 048dcfd — with nothing left waiting on them.

066 — resolution loses to a VRAM number

ART-04 asked whether a 512 px atlas cell should mean a bigger sprite on screen, or the same size at twice the resolution. Bigger is a whole-game layout change — every screen-space calculation, the measured pivot, the accessibility baselines all move. Higher resolution is far cheaper in code, a draw-time scale, and is the option that would have won on looks alone. It is rejected on performance: the sixteen-yaw library already measures 157.3 MB of uncompressed atlas VRAM, and quadrupling the area per cell takes that to roughly 630 MB on GL Compatibility — not a number to spend with no complaint driving it, and decision 056 already recorded the opposite call, accepting detail loss at distance on purpose. ART-01's sixteen-yaw heads bought the real fidelity win already, a turret that tracks instead of snapping, for 157 MB and 30 percent under the ceiling the PRD's own risk register warns about. This is the rare case where quality-first and no point the same way. Reopen only on a reported legibility complaint at zoom 1.0, never on a feeling that sharper would be nicer.

067 — a check that cannot fail

PRESSURE_FLOOR in sim/run.py asserts the player is pressed against reactor capacity. It has now been measured dead twice: 0 of 72 anchor-by-difficulty cells fail it, including under the four new capped-core policies, and including restricted to winning builds only — which was the original backlog item's own proposed repair. A check that cannot fail is worse than no check at all, because it implies coverage that isn't there. Raising the floor until it discriminates was the alternative on the table, and it is rejected too: a threshold picked to make today's data fail is fitted to that data, not derived from anything. The design property behind it is real and worth keeping — it's the one genuinely good idea the whole game rests on — but peak load ratio is simply the wrong instrument for it. What replaces the constant is a question with its own evidence to gather (LF-164), not another number chosen to make a graph turn red. All 24 anchors still grade clean with the check gone.

068 — the branch that argued back

19 of 20 .gd files were already indented in tabs, .editorconfig already pinned it, and the editor was settling the question by attrition anyway. main.gd is reindented as a standalone whitespace-only commit with a blame-ignore entry, so it doesn't poison git blame on every line it touches. The more interesting move is what got deleted: a 6,000-line worktree branch carrying the opposite choice, all 19 files reindented to four spaces. It was never going to be merged once tabs had 19-to-1 and a config file already saying so — keeping it alive was how this question stayed open for sessions. A branch is diligence when it represents work still being weighed. This one represented a vote that had already lost, still sitting in the tree as if the question were unsettled.

069 — closed, not merely unscheduled

Line of sight (TER-12) and a per-node power grid (WAR-11) were reserved for the owner since the PRD was written, and the PRD's own text already recommended against both. Both close outright rather than sit open in a way that reads as "coming eventually." Line of sight is the largest single work item in the programme and invalidates all 24 anchor grades on its own — a cost that matters more now than when the PRD was written, since the previous entry in this journal showed the grades are still moving under abilities the grader now models honestly. Stacking a rule that changes what every emplacement can reach on top of a grading model that doesn't yet track ability charge would compound two unsettled things instead of settling one. The regional grid fares no better on cost: relay nodes already deliver the interesting half of the idea, supply as ground you take and defend, for a fraction of what a full per-region rewrite of both rule engines would cost.

What ties the four together is not the subject matter, it's the shape of the delay. Three of these had been measured to death before this commit ever existed: the PRESSURE_FLOOR emptiness was measured twice, the atlas VRAM number had been sitting in the library since ART-01 landed, and tabs had already won 19-to-1 with a config file saying so in writing. The evidence was complete in every one of the three; what was missing was somebody saying the word. And the honest failure worth naming is that a branch was being used to keep a rejected indentation scheme alive, and a backlog item was being used to keep a check already shown twice to catch nothing alive — both of them ways of not deciding that look, from outside, exactly like diligence. Open work still under consideration. Neither was still being considered. Both were only costing sessions.

Also filed: the wrap is running the wrong check in the wrong place

The same commit files PRC-20 (#93), refined from the owner's own #90 with a fourth cause they hadn't named: the session wrap runs the full gate unconditionally, and now that every commit on main arrives through a gated pull request, that gate is largely re-proving what the PR flow already proved. The number behind it: tier 4 on the run that motivated the issue came to 1,755,759 ms — 29 minutes, of which rules parity alone was roughly 13 across 1,440 runs, and roughly 20 of more than 32 total wrap minutes had already passed with the commit and this journal still outstanding. PRC-05 already built the fix — a content-hash cache that skips parity entirely when nothing that affects it changed — and it simply isn't wired into the wrap's own path. Filed as the highest-priority item in the programme, ahead of any feature work, because what it's billing is the owner's own attention, not compute.
