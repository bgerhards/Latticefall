The fix, and the one line that matters

Proportional, not counted, reusing the existing ward_engage_1..6 bank. No new audio was authored.

rung 6 the instant the board is full, otherwise rungs 1..5 spread evenly over the builds before it — 1 + (n - 1) * 5 / (total - 1), integer division.scripts/anchor_view.gd, ward_cue_step()

Why the full-board case is a separate branch rather than a plain n * 6 / total. The bank's WARD_STEPS is a rising major pentatonic G3 to E4 at +0.30 dB per rung, with everything except pitch held identical across all six, authored “so the sixth is unmistakably the last one”. The split keeps rung 6 reachable only at n == total, so the top note lands on the last build and lands once — the same build the wards-full dialog line fires on. Both endpoints are pinned deliberately, because the endpoints are where the old bug lived: n = 1 is always rung 1, and total <= 1 is rung 6, because a one-emplacement board is full on its only build.

And a detail worth recording on its own: on a six-emplacement board the sequence is 1, 2, 3, 4, 5, 6 — rung for rung identical to the counted cue it replaces. That was the bank's design case, and the proportional mapping reproduces it exactly rather than approximating it.

The denominator is wards_total(), which is sim.effective_cap() — called, not reimplemented, the same number entry 57 established as the one the rules and the parity harness already agree on. anchor_sim.gd is untouched by this change.

How it was proved, which is the methodological bit

The 78-emplacement row was measured, not predicted. ward_cue_step() is static and pure, so a temporary export_state() field emitted the whole n = 1..78 table from the *running game*, and a scenario assertion printed it. Under the old code the same field read 1,2,3,4,5,6,6,6,…,6 — 73 consecutive top notes on a board the generator will happily produce. Both the temporary field and the temporary old-mapping line were removed afterwards; a grep for the marker they carried returns nothing, and the shipping diff is only the change itself.

One permanent addition survives from that scaffolding: view.wards.cue in export_state() — derived, not stored, so it cannot drift from what was played.

The reason both halves were silent, and it is the same reason

LF-228 and LF-232 hid for the same structural cause: the cue index was visible nowhere outside _on_built(). Filed as LF-235 — AudioDirector.sfx() has no cue log, so no scenario can assert what the game actually played. Every audio assertion in this project is really an assertion about the *caller's arithmetic*.

A bounded ring buffer of recent cue names would make “the brownout duck fired”, “the deny tone played and not the build tone” and “rung 6 played exactly once” assertable. None of those can be checked today. LF-174 already lists audio_director.gd among the zero-coverage scripts; this is the concrete mechanism behind that entry on the list.
