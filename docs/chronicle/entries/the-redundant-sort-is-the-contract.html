The redundant sort is the contract: 24× and 34× off O(emplacements × units)

WARdecision 072decision 058decision 027decision 030

WAR-02 and WAR-03 close the tick-cost gate that WAR-06's unit budget and the still-open board-size call in PRD §6 both depend on. _step() was O(emplacements × units) with an inner O(units) splash loop — 24,000 distance checks a tick at 60 emplacements and 400 units at 30 Hz. WAR-02 resolves every unit's position once a tick instead of once per pair; WAR-03 adds a uniform grid sized larger than any real range or splash radius. Together: 20.08 ms to 0.84 ms at 512 units / 60 towers / 24 segments (24.1×), 58.43 ms to 1.73 ms at 1000/80/32 (33.8×), both PRD bars met. Selection was tested directly rather than inferred — decision 058 is the reason why — and decision 072 records the one thing about a spatial index that is invisible in its own diff: a sort that looks redundant because every bucket is already sorted, kept anyway, because it is the entire reason the indexed and exhaustive paths never disagree.

_step() priced every tick as O(emplacements × units), with a splash loop inside that added another O(units) on top of it — 24,000 distance checks a tick at 60 emplacements and 400 units running at 30 Hz. That cost is the actual gate on scale: WAR-06's unit budget depends on it, and so does the board-size decision still open in PRD §6, because the honest input to that call is a measured frame cost at 400 units, not a guess at one. This entry is the two fixes that closed it, WAR-02 and WAR-03, both landed in the same working tree and both worth telling apart, because they were verified differently and failed differently.

WAR-02: resolve a position once a tick, not once per pair

Every tick, the old fire phase called the lane's point_at() three separate times per unit it looked at — once in the targeting scan, once again for the reveal check, once more in the splash loop — and it looked at units once per emplacement, so the same unit's position was recomputed as many times as there were guns in range of it. WAR-02 resolves every live unit's position exactly once per tick, after the movement loop has advanced its distance along the lane, into an index-parallel cache that the targeting scan and the splash loop both read instead of recomputing. The one deliberate exception is bus_load(): it runs before _step() in the tick order, against pre-movement positions, and sharing WAR-02's post-movement cache with it would silently change what decision 027 prices — so it keeps its own resolve, with a comment now saying why, rather than being “fixed” into a shared read.

WAR-03: a grid sized larger than anything that queries it

WAR-03 adds a uniform grid over that same per-tick position cache, rebuilt from scratch every tick rather than maintained incrementally — an incrementally-maintained index is a second place for the Python and GDScript engines to drift apart, and decision 072 rejects it for exactly that reason. CELL_W is 8.0 tiles in both engines, a constant and never per-anchor data, chosen larger than the longest range or splash radius in data/towers.json (mortar-emplacement: 6.5 tiles range, 1.5 tiles splash), so a query at any real emplacement only ever touches a small, fixed number of cells regardless of board size. The exhaustive scan was not deleted — it is reachable behind grid=None in Python and a null grid in GDScript — specifically so the two paths could be diffed against each other rather than trusted on faith.

Why the measurement is the deliverable, not the diff

Decision 058 is the reason this could not be verified by parity alone: a previous idle-rescan fix in this exact codepath passed 864 runs of parity and changed nothing measurable, because a change that passes parity has only proved it did not change anything observable — which is precisely what a no-op also proves. So target selection was tested directly rather than inferred from an aggregate grade. Four independent modes, all reporting zero differing selections between the indexed and exhaustive paths: a synthetic 512-unit / 60-tower / 24-segment board over 300 ticks; 300 randomised boards over 1,500 ticks; an LF-055-shaped case built specifically to have several structurally identical units alive on the same tick in range of the same guns; and every one of the 24 anchors, at all 3 difficulties, at every standard policy, driven through the real Sim.run() rather than a synthetic rig.

One structural proof sits next to the statistical ones and is the nicer of the two: wrapping point_at() and running an identical board once at 10 towers and once at 100 towers gives 1,024 calls per tick in both cases — a count invariant to tower count, which is exactly the property WAR-02 claims about itself. Before the change, that same count scales with tower count directly.

Parity, and why the Windows leg matters specifically here

The Linux leg is confirmed green, freshly run rather than read from cache: digest 52d5a4e66195, 1,440 runs identical. The Windows leg was started as this entry was being written and its result is not confirmed here — a machine running someone else's parity pass is not a machine to also drive a screenshot or a second parity run against, so this entry says only what it can stand behind.

Windows matters more for this change than for most. BAL-06 established that every parity run before it had been comparing CPython against the Linux Godot build while the owner plays on Windows, and LF-105 then measured that Windows Godot's atan2, sin, cos, pow, log, exp and tan diverge from CPython — parity has held so far only because the rules use none of them. A spatial hash is exactly the kind of code where someone reaches for one of those. This one does not: it uses floor and fmod, both measured byte-identical across all three runtimes, and the gate's safe operations check is green. Worth naming as a near miss rather than passing over — the trap was real, and this implementation happened to route around it rather than being designed around it from the start.

LF-098: the general fix beat the special one

An emplacement with nothing in range used to rescan every unit on the board, every tick, forever — measured at 2.19× cost at 8 towers / 32 units, rising to 2.87× at 100 towers / 800 units. WAR-03 closes it as a side effect: an idle gun now only scans the cells within its own range, so --all-idle now measures 0.74× — faster than the baseline it used to run nearly three times slower than. No targeted fix was written for LF-098, and none needed to be — decision 058 already records that a targeted attempt at this exact problem had been tried once and done nothing. The general fix arrived for an unrelated reason and happened to be the answer.

The ordering contract — decision 072

The actual risk in a spatial index is invisible in the diff, and decision 072 is what names it. Both engines' grid queries sort their merged candidate list on every call, even though each individual bucket is already sorted by construction from insertion order — and that sort looks, on a skim, like dead weight to delete. It is not: iterating buckets in their own order would be free, but it would make a tie between two units in the same cell depend on which of them entered the grid first, which is spawn history and container internals leaking into which unit a gun picks. That is PRD risk #3 by name, with LF-055 as its precedent. The redundant sort is what makes the ordering ours instead of the container's, and it is why the indexed and exhaustive paths provably pick the same unit on every tie, not just the ones a test happened to cover. GDScript keys its grid with a packed int (cy times a fixed stride, plus cx) rather than a Vector2i for the same reason — Vector2i hashing order is a Godot engine internal, and this index does not get to depend on one.

sim/coverage.py — the siting instrument that landed earlier the same session — needed no changes at all to keep working against the refactored engine, because _veteran_rank, _damage and _tick_once kept identical signatures and call sites throughout. Its own --selftest is green. A refactor this large leaving a fresh, unrelated subclass completely untouched is a good sign about both pieces of work.

As written, this work is uncommitted on lf/war-perf-core — sim/engine.py, scripts/anchor_sim.gd and tools/bench_tick.py — with the Linux parity leg confirmed and the Windows leg run but not yet confirmed complete.
