Silent and wrong: a guard built to stop that, doing exactly that

PRC

scripts/main.gd's reindent to tabs closes the mechanical half of decision 068, verified whitespace-only rather than assumed. The real story is what landing the previous entry ran into on the way past: the guard rail built to stop one agent's git stash sweeping five workstreams together made a brand-new file uncommittable by the documented workflow, and the failure mode was not a refusal — it was a published site with a dead link and nothing red anywhere.

scripts/main.gd was the last of twenty .gd files still holding four-space indentation. Decision 068 had already settled that indentation is tabs, and the other nineteen files were already there with .editorconfig pinning it — the editor was going to keep re-settling this by attrition either way. The transform is mechanical: n leading spaces become n//4 tabs plus n%4 spaces, preserving nesting exactly, 721 lines changed. Worth two sentences mostly for the verification shape — whitespace-only was proved, not asserted: git diff -w --stat printed nothing against the same commit that plain git diff --stat reports as 721 insertions and 721 deletions, and godot boots was run on top of gdscript parses, because main.gd is the main scene's script and a parse check alone would not have caught a broken boot. Decision 068 also called for deleting the 6,000-line all-spaces branch that had been keeping the rejected option alive; it doesn't exist on origin and isn't local, so there was nothing left to delete — the branch that had been arguing back was already gone.

The same pair of commits teaches git blame to look through the reindent: .git-blame-ignore-revs now lists 698d3d8, so a blame on any reindented line skips past the whitespace-only commit to whoever last touched the content. GitHub honours the file automatically; locally it needs one git config blame.ignoreRevsFile .git-blame-ignore-revs. The file states its own bar for admission, because a commit listed there is invisible to blame and a real change smuggled inside one would be unattributable.

The real story is what landing the previous entry ran into

While the previous entry in this journal — the four owner-gated decisions, published in 048dcfd — was being committed, the documented coordinator workflow silently published a broken chronicle page. git commit --only docs/chronicle committed the regenerated chronicle.json and index.html, and silently dropped the new entry page both of them link to, because --only commits tracked modifications and the new file was untracked. No error; the commit reported three files changed and looked complete. Naming the file directly then failed outright — pathspec ... did not match any file(s) known to git — and tools/hooks/guard.py's git-safety rule denies git add with no escape hatch, unlike rule_background (LF_ALLOW_BACKGROUND=1) and rule_raw_engine (LF_ALLOW_RAW_ENGINE=1), which both ship documented opt-ins. The retry loop failed five times running before anyone stepped back and asked why.

So a rail built to stop one agent's git stash sweeping eleven files across five workstreams had, as a side effect, made it impossible to commit a single new file — and the failure mode was not a refusal, it was a GitHub Pages publish with a dead link and nothing red anywhere. The guard exists precisely because silent-and-wrong is worse than loud-and-blocked; here, it produced silent-and-wrong. The way through was git update-index --add <path> — plumbing rather than git add, one named path, which cannot do the thing the guard actually defends against. That is the tell that the rule is too broad: the documented harm is a wide add sweeping other agents' files, and a single explicit pathspec cannot cause it. Filed as LF-166, with the fix left open between two shapes — give the rule the same LF_ALLOW_* opt-in the other two already have, or narrow it to deny only the wide forms and let an explicit single pathspec through.

Filed the same way in the same pass, by hitting it rather than by reading code first: LF-165, 584 tracked render PNGs, 224 tracked .import sidecars, and 360 more sitting untracked in every agent's git status before it reaches that agent's own edits. The game never loads a loose render — sprites.gd reads only sprites.json and the packed atlas pages — so the sidecars are build output of an editor import, not content. Left open rather than fixed here, because git rm --cached is an index operation and the index is shared across whatever else is running in the tree at the time.
