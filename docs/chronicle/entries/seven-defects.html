Seven defects, measured before a line of the plan was written

PRC

Profiling the real code against synthetic boards and unit counts, rather than guessing what would break on the way to a war-scale board. The whole game today costs 1.5 ms of a 16.7 ms frame — so the question was never whether there is headroom, only which thing runs out first.

Before a single Theatre Scale issue was implemented, the real code was profiled against synthetic boards and unit counts, to find out what actually breaks on the way to a war-scale board rather than guessing. The whole game today costs 1.5 ms of a 16.7 ms frame — so the question was never whether there is headroom, only which thing runs out first.

Four defects already shipping

  • An idle emplacement with nothing in range re-scans every unit on the board, every tick, forever — the empty-target path never resets its own cooldown. Measured 2.19x the cost of the same board with targets in range at 8 towers / 32 units, rising to 2.87x at 100 / 800.
  • _covered_by() tests every placed emplacement's effect type inside its own loop, so it costs O(towers) per unit even when nothing on the board has that effect at all — 24,000 wasted iterations per tick at 60 towers and 400 units.
  • The hit-flash lookup scans the entire live hit list for every drawn unit, roughly U^1.9 — 29% of all draw cost at 900 units.
  • drawables() is rebuilt and re-sorted four times a frame — once each for the shadow pass, the sprite pass, the glow layer and the additive FX layer.

Three that block the plan, not the game

  • render.py's calibrate() cannot converge at 384px or 1024px cells — it corrects orthographic scale from the width ratio only, so a one-pixel height shortfall never resolves. 256 and 512 only work by luck.
  • The board-saturation guard reads a tower's base draw_mw and never its upgrade.draw_mw, so an upgraded tower's real draw is invisible to the check that exists to protect the power decision.
  • Sprite legibility at zoom-out is a design question, not a camera feature. Fitting a 64x64 board needs 0.234x zoom at 100% interface scale and 0.117x at 200% — rendering a sprite at 30 to 60 px, likely below the point where one enemy is distinguishable from another. That needs a human answer before a camera can be built around it.

Also recorded, and revisited within a day: both rule engines compute lane-segment length as abs(dx)+abs(dy), with no square root anywhere, because Python's and Godot's floating point are not guaranteed bit-identical — decision 030's reasoning, and the reason the parity gate has stayed green. Diagonal lanes would reopen that question, so the axis-aligned rule was written down rather than quietly assumed safe forever. It would turn out to be half wrong the very next day — see decision 061, in the entry on the gate.

None of these seven were fixed here. They were found so that everything built afterward would be built on what the code actually does, not on what it was assumed to do.
