The binary the owner actually plays, tested for the first time

PRCBAL

1,152 parity runs so far had all compared the reference engine against the Linux build of Godot. The owner plays Windows. Nobody had checked whether the two agree — until now: 1,440 runs identical across CPython, Linux and Windows.

BAL-06, PRD risk #2 rated Blocker, closing LF-105. Every one of the 1,152 parity runs on record compared CPython against the Linux Godot build. The owner plays the Windows build, and the gate had never once tested it. It can be driven directly from this Linux machine, more simply than expected: the Windows console executable runs straight through WSL's own binfmt interop with no wrapper at all, because --headless never opens a window on any build, so nothing needs a virtual framebuffer either. Both new modes print the resolved executable path before anything runs, and error loudly rather than silently falling back to the Linux build if a platform cannot be resolved.

three-way parity ok — 1440 runs identical (python, linux, windows) — 24 anchors, 20 policies (up from 16 mid-run, because BAL-01's scheduled-action rewrite was landing at the same time, which makes this a real result on a moving tree rather than a permanent certification, and it says so), 3 difficulties.

This confirms rather than gets lucky: the rules use none of the operations measured to actually diverge between runtimes — tan disagreeing on 4.32% of samples, sin on 0.133%, cos on 0.120%, pow on 0.130% between the Windows and Linux math libraries — the exact operations decision 061's safe-operations check already excludes from both rule engines.

Timing is reported honestly and it is incomplete. The full three-way run took 989 seconds, but its last third overlapped a sibling parity run competing for the same CPU, so that figure is not trustworthy on its own. The one clean data point is anchor-01 run alone: 6.6-6.9 s on Windows against 7.4 s on Linux, so Windows is not the slower of the two. There is no clean per-leg split for the full run, because the three-way runner does not log per-leg completion — a real instrumentation gap, left open rather than papered over.

An earlier attempt died with an unhelpful "godot produced no parity output" that did not say which of the three legs had raised it; both error paths now name the executable, the anchor and the exit code. That earlier failure is attributed to the concurrent rules rewrite rather than to either platform — spot checks on both platforms passed individually once the rewrite had landed — but the record says plainly that this cannot be proven, only judged circumstantial.

The proposal going forward: run --three-way by hand before tagging a release, since it runs all three legs concurrently in one pass rather than two sequential ones, and it composes with sharding. No CI answer exists yet, because parity has never run in CI at all — the subject of the entry immediately before this one.
