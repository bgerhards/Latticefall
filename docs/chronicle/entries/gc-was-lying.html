The sweeper was lying about what it would delete

PRC

A blocker had been filed that morning, live, while two agents were running: the branch garbage collector proposed deleting the branch of an agent that was working in that worktree at that moment. It reads like data loss and it was filed as data loss. Reproducing it deliberately showed something more interesting — it could not have deleted anything, for two independent reasons, and the real bug was that git branch --merged decorates its output with a + for branches checked out in another worktree, which the parser did not strip. The tool was reporting a destruction it was incapable of performing. Which still cost a blocker-priority issue and a session's belief, and which stayed safe only by accident of a malformed name. The worse defect was found while fixing that one: every failed removal was silent and still counted toward “swept N items”.

LF-201 was filed the same morning it happened, which is the best kind of bug report. Two agents were running; a dry run of tools/gc.py printed this:

branch would delete + worktree-agent-a7712cc56b9f06fe1 (merged into main)

That agent was working in that worktree at that moment. The issue was filed as a blocker, with an argument that is entirely correct in the abstract: a killed process can be re-run; a deleted branch carrying an agent's work is gone. It was ranked above everything else on the process queue.

Reproducing it first, which is what changed the answer

The condition needs a worktree whose branch points at main with no commits yet — that is what makes a live branch classify as *merged*. git worktree add --no-checkout produces it for free, with no 150 MB checkout. Then the two commands the tool would actually have run:

commandresult
git branch -d "+ lf/repro-201"error: branch '+ lf/repro-201' not found
git branch -d "lf/repro-201"error: cannot delete branch 'lf/repro-201' used by worktree at …

Two independent guards, and the tool never got past either one. The first because the name it had built was not a real ref; the second because git itself refuses to delete a branch a worktree holds. Nothing was ever destroyed, and nothing could have been.

So what was broken

git branch --merged decorates its output. * marks the current branch — which the old parser did strip — and + marks *a branch checked out in another worktree*, which it did not. So a live agent's branch came back as the literal string "+ lf/thing", matched nothing in the checked-out exclusion set that exists precisely to protect it, and got printed as a deletion.

The tool was lying about what it would do rather than doing it. That is a smaller bug than data loss and it is not a small bug: it produced a blocker-priority issue, and a session that believed agent branches were being deleted. It also stayed safe purely by *accident* — normalise that name in some future refactor and the exclusion has to actually work. So it was made to actually work.

The defect found while fixing it, which is the worse one

Both removal paths ran subprocess.run(..., capture_output=True) with no return-code check, then incremented the counter unconditionally:

Every failed removal was silent, and still counted toward “swept N item(s)”. That is the same class of instrument as the retry loop this project once had that committed nothing twelve times in a row without ever failing — a number that reports success for work that did not happen. gc.py now checks every return code, prints each failure by name, and exits 1 if any removal failed.

What changed

  • --format=%(refname:short), so no decoration can ever reach the delete path.
  • %(worktreepath) from for-each-ref as the authoritative checked-out set, instead of parsing worktree list and hoping.
  • Branches considered before worktree prune. Pruning de-registers a worktree whose directory has vanished — and de-registering is exactly what disarms git's own refusal, the second of the two guards. Order matters here in a way it did not look like it did.
  • A KEPT line that names the worktree holding the branch, instead of a delete line that lies.

A selftest that is deliberately not in the gate

gc.py --selftest asserts both invariants against this repository's real refs, not a fixture. That is on purpose: the bug was a parsing bug against real git output, and a fixture of what someone *believes* that output looks like is exactly what let it through — the old parser was written against a correct mental model of * and an absent one of + .

It is not a gate check. It costs 1.45 s, almost all interpreter startup, to guard a tool invoked once per session at wrap — while tier 1 has about 1.7 s of headroom and tier 2 is already over its own budget. Adding it would be the same bad trade as raising a budget rather than removing a check, which is the move decision 067 refused. So it runs where the tool runs: the ship skill's sweep step now reads --selftest && --apply.

The general lesson

The issue text was written from the dry-run output, which is the most reasonable thing to write it from, and it was wrong about the mechanism — it described data loss that could not occur. Reproducing before fixing cost about ten minutes and changed both the severity and the fix. The backlog entry has been superseded rather than edited, the same rule the decisions log follows, so the record still shows what was believed on the day.
