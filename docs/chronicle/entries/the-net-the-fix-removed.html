LF-224 — the net nobody meant to have, removed by a correct fix

sim determinism used to return FAIL on sim/run.py's exit code, before it compared its two runs at all. And run.py --json exits 1 whenever an anchor is not clean. So the check had been serving, by accident, as an all-anchors-clean assertion — under the wrong name, with an empty message, because run.py writes its verdict to stdout and the check reported stderr.

Entry 54 — The acceptance criterion was not a selector, the-acceptance-criterion-was-not-a-selector — fixed the check to do what its name says. That is right, and it removed the accidental net. Entry 55, Four anchors, four different levers, then restored all 24 anchors to ok. The deliberate replacement was deferred until the grades were clean, on the reasoning that a check which is red on arrival gets disabled rather than fixed. They are clean, so it is built now.

tools/check.py gains anchor grades, tier 3. It shells sim/run.py --jobs 8 --json, parses the report, and puts every failing anchor's own problems strings in the message. It restates none of run.py's thresholds — what counts as unwinnable, as a single-solution level, as difficulty not biting, stays run.py's business. A second copy of a rule is the drift this project keeps paying for.

Why tier 3, and the reasoning is the interesting part

Tier 2 is unavailable. It is already *over* its own 28,000 ms budget (LF-178), and decision 067 refused to raise a threshold so the data would fit once already — the fix there is to move a check out, not to move the number again. Tier 4 was rejected because the regression this catches arrives almost exclusively as a data-only pull request: entry 55 moved four anchors' capacities and slot layouts and nothing else. Tier 3 is the PR tier, and a check that only runs nightly lets an unwinnable anchor sit on main until the next scheduled run. The cost is named rather than hidden: tier 3 goes from 204 s to 265 s.

One thing worth a line on its own. tier counts is a tier-1 check that asserts check.py's own docstring counts against its CHECKS registry on every run, so adding a check without updating the prose turns the gate red. That is deliberate — a count written into prose here rots within a day, so it is asserted rather than trusted. Docstring updated in the same change: tier 3 = 38, tier 4 = 41.

LF-229 — the branch that no shipped board could reach

sim/coverage.py's verdict() printed "no material near-zero tail (9% of emplacements)" for a generated 48x48 board whose own presence ceiling is 11.9% — a board where the best legal positions available anywhere reach 12% of the live wave. The (0) branch tested the near-zero tail and returned before (b) ever consulted board_presence_ceiling.

(b) is now tested first and unconditionally. The order is (b) then (0) then (a) then (c). All 24 shipped anchors keep their exact verdict — 0 of 24 moved, verified by running the pre-change and post-change verdict() over one cached 24-anchor report set, so the comparison cost no simulation at all.

The ordering argument was made for all four branches, not just the pair

This is the part worth recording, because it is the part that would otherwise be re-derived. (a) deliberately stays after (0). It is a ratio against the board's own ceiling — headroom, not outcome — and promoting it above the tail test relabels twelve shipped anchors from "no material tail" to "(a) siting", on boards where every emplacement is doing work. (b) is an absolute claim that no outcome is reachable anywhere, so it needs no tail to be true. Outcomes rank above headroom; a claim about what could have been better ranks below both.

The correction — and it lands on act 1

LF-229's own ticket said all 24 shipped ceilings are 75–95%, so the short-circuit could only ever mask a low ceiling on a board unlike any that ships. That premise was wrong. Measured while fixing it, at range basis 8189779cd568:

anchor-0365.3%under

No label moved when the ordering was fixed, but only because those four already carry large near-zero tails and were reaching (b) by another route. (LF-234 records that band as 22–31%; sim/coverage.py's own note says 19–31% — the conclusion is the same either way, and the discrepancy is recorded here rather than smoothed over.) So the masking window is narrower than the ticket claimed and real — and what sits under the threshold is act 1's entire opening stretch.

Those are boards where the level's own slot-and-range budget is the limit, not the player's siting. Filed as LF-234. It is the same conclusion LF-187 reaches from the other direction — a fixed absolute range covers a shrinking fraction as lanes lengthen — and the same four anchors entry 55's re-balance found thinnest. Worth treating as one finding rather than three.

The gate, and what this entry does not have

A tier 4 run finished before this was written: 39 passed · 0 failed · 2 skipped, out of 41 checks — up from 40, and the new one is among the 39 that ran and passed. The two skips are rules parity and rules parity (windows), held back by the content-hash cache at digest 78921592b4c5 because no rule or data file changed in this branch. That is cached, not run — it is not a pass, and it is stated that way here for the same reason the gate's own tally line names every check that did not run: a green partial result that reads like a full one is the failure the tiering exists to prevent.

The work sits on lf/prc-verification-holes and is uncommitted as this is written, so there are no commit hashes here. And there is no screenshot: the evidence in this entry is a check message with two anchors' problem strings in it and a verdict label that changed on a board that does not ship, and neither of those is a thing a picture of the game can show.

Seven entries in one day

Three of them found the fault in an instrument rather than in the game. One built a tool that then found a real bug. One fixed four anchors with four different levers. One found a cue the player could never hear. And this one closes the two holes the others opened.

A verification layer is not a thing you build once. It is a thing that acquires holes exactly as fast as the code under it changes, and the only defence is noticing when your own fix removed something.
