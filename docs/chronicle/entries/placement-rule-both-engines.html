PLC-02 — where you may build is now a rule, in both engines. Bounds, lane standoff, overlap, replacing PLC-01's exact-match stub that accepted only an anchor's authored slot positions.

But the parity result is the weak evidence, and that is the entry

Neither engine's _try_build() calls _is_placeable() at all. Both source their candidates from _slot_priority(), which reads the authored slots — expanding that set is PLC-04's job. So none of the 1440 parity runs ever asks the predicate about a position outside anchor["slots"]. Identical parity therefore means *nothing regressed*. It does not mean the new rule is right.

A green gate that cannot see the thing you changed is a shape this project keeps finding — a tier-2 budget that was never actually met, a renderer whose output matched its input while both were wrong, a ruleset exercised against zero real references. This is the same failure mode, caught before it shipped as proof of something it did not prove.

So the rule was proved directly instead

  • 48,837 sampled positions, grid step 0.37, across all 24 anchors, extending one tile outside every board edge, with two emplacements pre-placed per anchor to exercise overlap. Dumped from CPython and from a headless Godot --script run. diff between the two dumps is empty.
  • Exact-boundary cases at 1e-9 either side — the one-in-a-thousand parity failure the spec warns about — both engines agreeing on all three rejection reasons.
  • Term order is identical character-for-character, not merely algebraically equivalent: abx*abx + aby*aby, dx*dx + dy*dy, r + FOOTPRINT_RADIUS. Floating-point addition is not associative, and on an exact boundary that is the difference between legal and illegal — which is the entire reason the parity gate exists.

Squared comparisons throughout, no square roots. The path is sampled as segments, pairwise over waypoints, never at _slot_priority()'s steps resolution — that sampling is a grader heuristic and is allowed to be approximate, a rule is not.

And the honest ending

A player still cannot build anywhere new. LF-197 is confirmed blocking at every layer it named: anchor_view.gd's hovered_slot = Vector2i(roundi(t.x), roundi(t.y)) rounds the mouse before anything downstream sees it, and available_slots() still enumerates anchor["slots"] rather than the predicate. The rule is correct and unreachable.

That matters because of what started this: the owner said most turrets could barely reach anything (LF-176), decision 074 proved the residual is slot geometry, and free placement is the fix — but only once PLC-06/PLC-07 land. The owner's own play feedback since, LF-200 (WASD should pan the camera, not step the cursor), belongs in that same change, because it touches the same input path. Two rule issues landed today and neither is yet visible in play.

Also filed
