The failures, given real weight

A journal that only records what worked is a lie by omission. Four things went wrong this session, and each is recorded here in the same detail as anything that shipped clean.

Decision 058: a fix that passed 864-run parity and did nothing

An idle emplacement re-scanning every unit forever — the first defect named in the measurement entry earlier in this journal — had a proposed fix: retry on the next tick rather than the same one. It was implemented in both rule engines. It passed parity across 864 runs. It changed nothing at all — measured, not argued: stripping the change back out left a full detailed grade of all 24 anchors and three difficulties byte-identical, 27,138 lines. The reason is arithmetic rather than a mistake in the code: the value the fix scheduled for the next tick was already the value the current tick would hold one step later, so the retry it added was already happening on its own. The one change that would have actually skipped real work — a longer retry interval — would have been a balance change wearing a performance change's clothing, and nobody had signed up to make that call casually. The fix was removed rather than kept as a harmless comment, because dead code sitting in the hottest loop of the rules, mirrored across two languages forever, is not free, and a reader would reasonably assume it does something.

The wider point is why this is a journal entry rather than a line in a commit message: a change that passes verification has only proved it changed nothing observable — which is exactly what a no-op also proves. A separate benchmarking tool exists now specifically so the other half of any performance claim, the actual gain, has to be measured too, not just its safety.

A stash that swept eleven files across five workstreams

An agent working alongside several others ran git stash to get a clean baseline for a before/after comparison. It took eleven files belonging to five different pieces of work with it and left the shared tree looking exactly like the last commit. For several minutes, every other agent in that tree was reading committed history instead of its own uncommitted edits — which raises no error at all, it just quietly makes any measurement taken in that window describe code nobody had actually written. It was recovered because the stash happened to get popped again, not because anything caught it in the moment.

The rule that came out of it: an agent never runs stash, reset, checkout with a path, or add. A coordinator commits with a path-scoped commit inside a lock-retry loop instead, and a proper worktree-per-workstream setup is the actual fix that makes the whole class of mistake structurally impossible rather than merely against the rules.

A one-line change that returned 1,152 empty parity rows

Wiring the last of nine recovery effects looked like a one-line read inside the rules file. It took the parity harness down instead: the harness preloads the rules with no autoloads available at all, so one reference to an autoloaded singleton made the whole rules file fail to load — not fail a test, fail to load — and every one of 1,152 parity runs came back as an empty result, which then crashed the harness itself on a lookup that named the harness, not the actual bug. Meanwhile the ordinary parse check stayed green throughout the entire episode, because it resolves autoloads from the project configuration and the runtime parity harness does not. The fix follows a standing rule directly: a recovery effect has to transform the simulation's inputs, never reach into a live singleton, and it was rewritten that way in one line once the actual cause was finally found.

The atlas that made everything flat grey

Raising the sprite cell size to 512 px was tested end to end — the render pipeline converges at that size, the packed page fits comfortably under this machine's measured texture-size ceiling, and a full library rebuild takes about two and a half minutes. Every real material in the game rendered as flat placeholder grey anyway, because a separate constant elsewhere in the engine still hardcoded the old 128x64 tile size, and the sprite loader's own size check failed silently into its placeholder path instead of raising an error. This was caught by sampling actual pixel colour against the expected material colour, not by looking at the frame — which is the only way it would have been caught at all, because a uniformly grey board reads, at a glance, exactly like a lighting change rather than a broken asset pipeline. The change was reverted back to 256 px and a real render was verified again before anything was reported as working.
