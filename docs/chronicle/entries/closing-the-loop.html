Closing the loop

The last change of the session was about work being visible somewhere other than a commit log.

The issue-projection tool had a create verb and a sync verb, and no verb for finished, so the projection onto GitHub could only ever grow. Twenty-nine of this session's issue specs were implemented, verified and committed while every one of their corresponding issues sat open on GitHub, and the owner noticed before the tooling did. A close verb now exists, and it requires a note: what landed, and how it was proved — because a bare close leaves the evidence sitting in a commit message nobody browsing the issue would ever think to go find. Twenty-nine specs closed this way; forty-five stayed open.

And this journal. It exists because a commit log is a fine record of what changed and a poor one of why any of it mattered, or of what went wrong along the way. Two rules apply to it going forward, the same two that already apply to the project's own decision record: it is append-only, so a later entry that overturns something written here says so and links back rather than quietly editing history, and the failures stay in — a journal that only records what worked is a lie by omission, and this session gave the entry on that subject, earlier in this journal, plenty of material to prove it with. It publishes as committed, pre-generated HTML with no build step at all, deliberately, so there is no toolchain here that can rot between now and whoever reads it next.
