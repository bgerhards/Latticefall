The gate: eleven minutes, five seconds, and a check for every failure that already happened

PRCdecision 061

tools/check.py was 18 checks and roughly eleven minutes, every time — run at the end of a task rather than during it, exactly when it is least useful. By the time this session closed it was 27 checks with a five-second first tier, running in CI, and enforcing two things that had already gone wrong once.

The gate — tools/check.py — was 18 checks and roughly eleven minutes, every time, which is why it got run at the end of a task rather than during it, exactly when it is least useful. By the end of this session it was 27 checks with a five-second first tier.

Enumerate from git, not from the filesystem

The gate used to walk the tree with a hand-maintained skip list, and that list had already failed once — an agent worktree carried its own stray copy of the terminology reference and scored six false hits against the actual file that is the authority on those terms. Switching to git ls-files needs no denylist at all, because a file has to be tracked to be seen: the false positive becomes structurally impossible rather than merely denied. On this machine, where every filesystem stat crosses a virtualisation boundary, it is also dramatically faster — the banned-terms check alone went from 31,906 ms to 1,393 ms, and the three converted checks together dropped 45.7 seconds off every run.

A GDScript parse check was moved to run before the engine even boots, because a parse error there is a hang or a blank frame, never an error reported at the actual failure site — it had already cost real diagnosis time five separate times in one session before this landed.

Tiers, and the rule that makes them safe

Tier 1 is nine checks in under five seconds and opens no window; tier 2 adds six subsystem checks for about fourteen seconds; tier 3 and tier 4 — all of it, including 1,152-run parity — are what the gate always was. The part that matters more than the speed: a check a tier excludes reports skip, with a reason, and stays in the JSON output rather than disappearing from it. An absent entry reads as a pass to anything consuming the file, and a green partial run that looks like a full one is the exact failure this exists to prevent. A --budget flag turns each tier's time limit into an assertion, so a tier whose cost silently doubles fails outright instead of quietly stopping being used — which is exactly what caught the next batch of checks below going over budget.

A gate that runs somewhere other than this machine

The whole verification story had lived on one machine with a Windows-side art tool, a Linux engine build and a pile of LFS sprites, so nothing had ever run in continuous integration. The new workflow runs tier 1 — nine checks, about five seconds — on every pull request, checked out with LFS turned off entirely, because tier 1 needs none of those bytes. Its pre-commit and pre-push hooks were written and deliberately left uninstalled: seven agents were committing through this repository at the time, and a hook failing on someone else's in-flight file would have blocked all of them.

Decision 061: the safe operation set was half right

Decision 030 banned square roots from both rule engines, reasoning that Godot's Vector2 is float32 and its distance function 'is not correctly rounded'. That bundled two different claims, and a probe — 100,000 float64 pairs across five value regimes, run on CPython, Linux Godot and Windows Godot, comparing raw IEEE-754 bytes — found only one of them true. sqrt itself matched 100,000 of 100,000 samples on all three runtimes; IEEE-754 requires it to be correctly rounded, and both engines issue the identical instruction for it. The real culprit was Vector2.distance_to, a float32 helper: on two million points placed exactly on an integer radius, it disagrees with the equivalent float64 computation on a boundary test 10.2% of the time. The trigonometric and transcendental functions fared worse still — tan diverges between the Windows and Linux/CPython runtimes on 4.32% of samples, sin on 0.133%, cos on 0.120%.

The corrected safe set — the four arithmetic operators, sqrt, fmod, floor, min/max and comparisons — is now a tier-1 gate check that parses both rule files rather than grepping them, because a regex misses an aliased import and false-positives on a comment discussing the banned names. It was proved red three separate ways before being trusted, by breaking each real file in place and restoring it byte-exact: a banned sin call, a float32 distance_to call, and a rules file quietly referencing an engine-only global that a bare parse check cannot see failing at all. That last one is the subject of its own entry, later in this journal.

Parity got slower before it got faster

Parity is the project's core guarantee and its worst bottleneck, and this session made it worse before making it better: 864 runs at roughly nine minutes when the day opened, 1,152 at roughly ten after four new grading policies and multi-lane paths landed — past the point it could still run inside the tool harness's own command timeout. The fix is a digest over everything that can actually change an outcome: the rule files, every tracked file under data/, and the engine binary's own version string, because an engine upgrade can move floating-point behaviour with no repository diff at all. A cache hit is loud about it — the tool prints what it skipped and when it last verified, and the gate reports the check as skip, never a silent ok. Sharding, when a run is actually needed, uses measured per-anchor cost rather than splitting the anchor list evenly: anchor-24 costs 22.7 seconds against anchor-01's 1.58, a 14.4x spread, and bin-packing against that measurement holds a four-way split to 1.4% deviation from the mean, against 32.2% for round-robin and 61.5% for a naive contiguous split.
