The instruments were standing where the player never stands

PLCTSdecision 080

LF-228 — a dialog cue that could never fire, and nothing noticed for two milestones. anchor_view.gd computed ward engagement as placed + available_slots(), and available_slots() is the authored slots still free — so once PLC-01/PLC-02 made placement continuous the denominator grew with every build: 9, 10, 11 … 16 across eight free placements on anchor-01. wards-full was unreachable; wards-half arrived at the cap. On an anchor authoring no slots at all, both cues fired on the first build. It hid because every automated path in this project — the grader, the scenarios, the autobuild — builds on authored slots first, where the wrong expression is coincidentally correct. Fixing the trigger then made a second defect audible: the lines still quoted counts from when both anchors had six slots.

The previous entry — The generator was not the deliverable, the-generator-was-not-the-deliverable, merged as #144 — built tools/genboard.py and closed on the observation that the measurement the tool made possible was worth more than the tool. This entry is one of those measurements, and it is not about scale at all. The generator authors 78 emplacement slots on a 48×48 board, and running the game on a board that size made a bug visible that had been sitting in a shipped file for two milestones.

The expression, and why it can only be wrong

scripts/anchor_view.gd::_on_built() computed the ward-engagement total as sim.placed.size() + sim.available_slots().size(). available_slots() returns the authored slots not currently occupied, and occupancy is an exact (x, y) equality test. Free placement — PLC-01 and PLC-02, decision 080 — made positions continuous, so a freely placed emplacement almost never lands exactly on an authored coordinate. The denominator therefore grows with every build.

So the wrong expression is correct under every automated path this project has — the grader, the scenarios, the autobuild. Only a human free-placing hits it. That is worth stating plainly: a project that verifies almost everything through headless automation built a blind spot exactly where the automation and the player diverge.

The fix is a call, not a reimplementation

The denominator is now sim.effective_cap():

anchor_sim.gd:400 — max_emplacements if max_emplacements > 0 else anchor.get("slots", []).size() — is the same quantity build_at() refuses past and Sim._try_build() uses. One number, already shared between the two rule implementations, already parity-verified. anchor_sim.gd was not modified.

Proved end to end through a real scenario on anchor-01 with eight free positions:

How it was verified, because it dodged a known trap

The hook is export_state() — view.wards.{engaged,total} — not a print marker. tools/scenario.py already relays its summary with every assertion's observed value, so the numbers are visible with zero new print prefixes. shot.py filters relayed markers by prefix and has silently eaten three working hooks before now; this change needed no edit to main.gd, shot.py or scenario.py at all. The bug was silent for exactly the reason the hook fixes: nothing could see total, and the only symptom was a line that never played.

An extra finding fell out of it. An anchor with neither slots nor max_emplacements has effective_cap() == 0, so build_at() refuses every build outright — the degenerate case is already unreachable in the rules, and under the fix the total > 0 guard correctly keeps both cues silent.

Fixing the trigger made a second defect audible

The cues were authored when both anchors had six slots. anchor-01 now authors 8 and anchor-24 authors 12. So with the trigger restored, the player would hear a line naming three wards at the fourth of eight, and a line naming six of six at the eighth of eight — and on the finale anchor, at the twelfth of twelve. Shipping the trigger fix without the text would have been worse than shipping neither, so three lines were rewritten so that no cue quotes a count at all:

triggerbeforeafter
anchor-01 wards-halfThree wards engaged. Ring's half live.Half the ring reads engaged. Rest when you can afford it.
anchor-01 wards-fullSix of six. Ring's fully engaged.That's the last ward. Ring's fully engaged.
anchor-24 wards-fullSix of six. Last ring Meridian lights on this order.Every ward engaged. Last ring Meridian lights on this order.

The constraint was structural rather than stylistic. PLC-05 lets an anchor set max_emplacements above its authored slot count, PLC-04's lattice places anywhere legal, and the LF-080 generator derives 78 emplacements on a 48² board. Nothing tracks the relationship between a dialog line and the anchor's capacity — there is a gate check binding a mission brief to its reactor rating (dialog capacity) and no equivalent for this. So the lines were written to be true at any capacity: "half the ring" is the proportion the trigger actually tests, "the last ward" names the boundary it fires on, "every ward" is a universal quantifier.

One line was already correct and was left alone as the model — Okonkwo's "Full ring, eleven-year-old hardware, and it still locks true. Somebody built this to last." It never quoted a number.

LF-207 was assessed and deliberately not done

PLC-06 left a 1-tile fallback scan in anchor_view.gd because PLC-04 did not exist yet, and LF-207 says to replace it with PLC-04's ordering once that landed. It landed this morning. The assessment says leave it, and the reasoning is worth recording rather than re-deriving next time.

PLC-04's GDScript lattice is a private method on a SceneTree MainLoop (parity.gd:472-587), not a class and not preloadable, depending on two file-local consts. The Python side is module-level and memoised on the Anchor dataclass, so extraction has no Python counterpart to mirror. Reuse therefore means a new preloadable module that both parity.gd and anchor_view.gd load — which drags in a tools/check.py safe operations registration, an edit to the one file whose failure mode is 1,152 empty dictionaries rather than an error, and a full tier-4 re-baseline including the Windows leg.

And a second point that outlives the ticket: even after extraction, anchor_view.gd would gain only the ordering. PLC-04's actual candidate choice is _try_build()'s lane round-robin by per-lane maximin, entangled with policy preferences, caps, overdraw, reserve and per-lane arclength state. "One candidate ordering in the project" is achievable for the lattice; the consumption rule is a second thing. autobuild()'s own docstring already claims it "builds the way the cheap-mass policy would" — which it does not, and would not, from the lattice alone.

The current divergence is real but narrow: the fallback runs only when authored slots are exhausted and placed < effective_cap() — today that is anchor-11 alone, and only under --autoplay. Revisit when LF-226's anchor-11 autobuild scenario is written, since that is the one thing that would exercise it.

Filed

  • LF-232 — the audio cue is still counted. _on_built() plays ward_engage_%d with clampi(n, 1, 6), so builds 7 through N all replay ward_engage_6. The sound effect stops counting at exactly the number just removed from the text. At 78 emplacements a counted cue is meaningless, so the recommendation is proportional rather than counted.
  • LF-233 — rename available_slots() to unoccupied_authored_slots(). Three callers left, all meaning "an authored position nobody has taken yet". The name is what made the bug read as correct.

What this entry does not have

The work sits on lf/eng-ward-engagement and is uncommitted as this is written, so there are no commit hashes here. A tier-4 gate is in flight and no verdict is stated — that belongs in the entry that actually has the result. There is also no screenshot, deliberately: the proof here is a denominator that reads 8 on every build and two trigger lines with frame numbers on them, and a picture of a board with eight emplacements on it would show none of that.

Six entries, and the last one found this one

The generator built in the previous entry found this bug — it authors 78 slots on a 48×48 board, which made a growing denominator impossible to miss. And the bug survived two milestones because every automated path in this project builds on authored slots, so the wrong expression was right everywhere the machines looked.

The instruments were not wrong this time. They were just standing somewhere the player never stands.
