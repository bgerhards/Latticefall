The hang that never was

rules parity (windows) has now run on hosted CI for the first time ever, closing BAL-06's gap and the CI half of LF-105, the project's only blocker-severity backlog item. The proof is a real check, not a diagnostic:

parity ok — 360 runs identical (gdscript vs python) [shard 0/4] [windows]run 30700674063, shard 0/4, windows-latest — 9m22s, zero divergence

Why it matters, restated as a measurement rather than a claim: every one of the 1440 existing parity runs compares CPython against Linux Godot, and the owner plays the Windows build. Across 100,000 float64 samples, Windows Godot (MSVC UCRT) diverges from CPython and Linux Godot (glibc) on atan2 0.084%, sin 0.133%, cos 0.120%, pow 0.130%, log 0.031%, exp 0.069% and tan 4.32%. The rules use none of those operations today — tools/check.py's safe operations check (decision 061) is what keeps that true by design — so cross-platform parity had held by accident, not by design, and until this run, nothing had ever watched it.

But the diagnosis is the story, because the first attempt failed in the most misleading way available

Beat 1 — it looked exactly like a bug already on file. The unsharded run died at 29 minutes: Godot printed its version banner, then produced nothing for the full 1700s internal timeout. That is the exact symptom gate.yml's own header and decision 071 describe for a checkout that was never imported — a class_name global or a font preload() blocking on missing .godot/ cache content. The coordinator read the log, matched it to the precedent, and called it near-certain.

Beat 2 — it was not that, and it was proved rather than accepted. An --import pass was added on that hypothesis and measured not to help: a CPU-time poll taken immediately after --import was identical to one taken before it. The import step was removed again; it survives only in the branch's diagnostic commits and in the workflow's header, which now warns the next person not to re-add it.

Beat 3 — it was never hanging at all. Single-anchor runs finished in 20–30s, ruling out a launch hang. A probe proved DirAccess.open("res://data/anchors").get_files() resolves in about 1ms, ruling out the one code path an unfiltered run takes that a filtered one does not. Sweeping anchors individually showed a rising cost trend — 24.1s, 33s, 39.1s, 48.1s for anchor-01 through 04 — and 562s for 360 runs extrapolates to about 1800s for the full 1152, a hair over the 1700s timeout. It ran out of clock. Sharding, not a longer timeout, was the fix — exactly what parity-shard.yml had already proved for Linux.

Beat 4 — the false signal that made the wrong answer believable, and this is the keeper. PowerShell's $proc.CPU / Process.TotalProcessorTime read a flat zero through a run that provably did correct work: anchor-05 alone completed with fully valid PARITY_JSON for all 48 of its combinations while the metric claimed 0% CPU the entire time. "No output plus no CPU" reads as wedged when the real state was "working, slowly." Filed as LF-191. The workflow header now says to check wall-clock against the single-anchor smoke baseline (about 20–30s) first, and not to trust $proc.CPU on this runner.

There is a general lesson worth naming: a symptom matching a known, well-documented, previously-expensive bug is exactly when you are most likely to stop looking. Decision 071 was real, its write-up was good, and its existence is what made the wrong diagnosis so easy to reach for.

The trigger, and its cost

Owner-approved and narrow on purpose: path-filtered to sim/engine.py, scripts/anchor_sim.gd and scripts/test/parity.gd — the only three files this check can catch a regression in — plus a weekly schedule and workflow_dispatch with a single-anchor smoke path that skips the matrix. About 9.5 minutes per shard across 4 shards is about 38 job-minutes, billed at Windows' 2x rate, or roughly 76 Linux-equivalent minutes per full run. Every-PR was rejected on that number. The cost is written into the workflow's first comment block so it is not re-litigated.

And one more thing landed alongside

main was protected by nothing at all, which nobody knew. A repository ruleset named main with enforcement active configured deletion protection, non-fast-forward protection and a pull-request requirement — but its conditions.ref_name.include was an empty list, so it applied to no refs. GET /repos/.../rules/branches/main returned []. The classic endpoint actively misleads here: /branches/main/protection returns 404 Branch not protected, which reads as "nobody set this up" rather than "somebody set it up and it targets nothing."

Same shape as decision 071's nightly.yml pointing at zero registered runners: configuration that looks live in the interface and is inert. That is now twice in this project, which makes it a pattern worth naming rather than an anecdote. The fix was drafted, diffed byte-for-byte against a live fetch, and held for owner approval before being applied, because it starts enforcing a PR requirement that had never actually been enforced. Filed as LF-193; confirmed here, against the live endpoint, that it is now applied — /rules/branches/main returns all four rules, including required_status_checks naming the three checks the repository actually wants required.
